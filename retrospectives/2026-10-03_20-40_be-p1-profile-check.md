# Ретро: `be/p1-profile-check` — проверка профиля до оплаты

**Задача.** `POST /api/profile-checks` и `GET /api/profile-checks/:id` по готовому контракту: `scrape → facts → analyze` до оплаты, гардрейлы, кэш 24 ч, лимиты на проверки.

**Как решали.** Оркестратор → исполнитель (sonnet, цикл 5 ходов) → проверяльщик (opus, карусель 01–09) → чек оркестратора (typecheck, lint, 383 теста, build, prettier).

**Решено:** да по коду; `[x]` ждёт живого прогона: `HASH_SALT` и Upstash во всех окружениях Vercel (заводит Сергей), `db:migrate` миграций 0001–0003.

**Ключевые решения.**
- Асинхронно: POST создаёт запись `checking` и запускает фон через `after()`; `maxDuration = 300` литералом (Next читает статически), дедлайн фона 280 с, GET закрывает зависшие `checking` через 330 с. Обновления статуса только из `checking`: проснувшийся фон не затирает закрытую запись.
- Статус в таблице `profile_checks`, а не в Redis. Хэши IP и токена (HMAC с `HASH_SALT`), на экран только поля `CheckedProfile`.
- Кэш 24 ч по `checkedAt` для `ok` и `minor_detected`; копия — новая строка под новым владельцем, чужой `id` не отдаётся.
- `scrapeProfile` теперь отдаёт `snapshotId` (открытый вопрос из analyze закрыт).
- Лимиты Upstash; `env.ts` принимает и `UPSTASH_REDIS_REST_*`, и `KV_REST_API_*` (имена Marketplace). Без Redis: dev пропускает с предупреждением, production — 503.
- GET только владельцу: чужой, несуществующий id и отсутствие cookie дают одинаковый 404.

**Что поймал цикл 5 ходов исполнителя.** Кэш продлевал сам себя (копия жила от своего `createdAt`) → `checkedAt`; голый sha256 по IP перебирается → HMAC; импортированный `maxDuration` ронял сборку; парсер ссылок отсекает `instagram.com@evil.com` и пути `/p/`, `/reel/`.

**Что поймала карусель.**
- IPv6-клиент обходил лимит, меняя адрес внутри своей /64 → лимит по сети /64.
- В production без `HASH_SALT` бралась запасная соль из публичного репо → теперь 503.
- Лимиты не совпадали с roast-engine («5 проверок в час на устройство и IP») → приведены, тест сверяет с документом.

**Что сделать лучше.**
- Оркестратору — давать исполнителю цифры лимитов из документа, а не «выбери разумно»: расхождение поймала только карусель.

**Передано дальше.**
- `profile_checks` хранит ник, имя и аватар чужого человека без срока → добавить в `architecture/data.md` и в `be/p3-retention-cron`.
- BotID на `POST /api/profile-checks` нужна правка FE — задача Сергею.
- Гонка двух одновременных POST одного ника (оба идут в Apify) — при наших объёмах терпимо, режут лимиты.
- Дневной потолок трат — задача `be/p1-cost-log`.
- Ложный `minor_detected` блокирует ник на сутки.

**Было → стало.** Было: шаги scrape и analyze без входа снаружи. Стало: публичная проверка профиля с поллингом, кэшем и лимитами, закрытая по умолчанию в production.
