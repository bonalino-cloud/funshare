# Ретро: `be/p1-orders-promos` — цены, заказы, промокоды

**Задача.** `orders`, `promo_codes`, `promo_redemptions`, расчёт цены на сервере по тарифам, атомарное списание кода, освобождение при провале, лимит на перебор (roast-engine §9.1–§9.3, §7.1a).

**Как решали.** Оркестратор → исполнитель (sonnet, цикл 5 ходов) → проверяльщик (opus, карусель 01–09) → чек оркестратора (typecheck, lint, 492 теста, build, prettier, SQL глазами). Ветка взята от `be/p1-profile-check` (PR #49 не слит): нужны `hash.ts`, `ratelimit`, `clientIp`.

**Решено:** да по коду; `[x]` ждёт прогона SQL на Neon (`db:migrate` 0001–0004 и ручной сценарий: последний код двумя заказами, release).

**Ключевые решения.**
- Цена только на сервере: Поджог 0, Кострище 9900 копеек; скидка `floor(list × percent / 100)`, равенство `list − discount = final` по построению.
- `neon-http` без интерактивных транзакций → списание одной командой из трёх CTE (UPDATE счётчика с условиями окна, тарифа, лимитов на человека → INSERT заказа → INSERT использования). Падение любого INSERT откатывает и счётчик; гонку на последний код закрывает перепроверка `redeemed < max_redemptions` после блокировки строки.
- `payment_required` не создаёт заказ и не тратит код: статус `created` придёт с билингом.
- Проба Поджога через тот же `orders` (причина `first_free`): частичный уникальный индекс по устройству; по IP до 3 проб — мягче буквы §7.1a, чтобы не бить по общему IP.
- `releaseOrder` одной командой, повтор ничего не меняет; проба возвращается человеку.
- Перебор: 5 неверных за 10 минут по IP и устройству, плюс атомарное окно 30 любых попыток против пачки параллельных запросов.

**Что поймал цикл 5 ходов исполнителя.** `createOrder` не отдавал `id` для release; `ON CONFLICT` по `generation_id` оставил бы списанный код без заказа; пачка запросов обходила проверку «неверных» до записи.

**Что поймала карусель.**
- Утечка по времени: существующий код отвечал за 2 запроса, несуществующий за 1 → один запрос `findPromo`.
- Своя регрессия проверяльщика: drizzle писал колонку без имени таблицы, подзапрос считал `r.id` вместо `promo_codes.id`, лимиты на человека молча не работали бы. Поймано на шаге 08, закреплено тестом.

**Что сделать лучше.**
- SQL с деньгами без живой БД проверяется только глазами и тестами на строку запроса. Нужен способ гонять такие запросы на временной базе (Neon branch или локальный Postgres) — предложить Денису.

**Передано дальше (`be/p1-generations-api`).** `generationId` выдаёт сервер; вызывать `guardPromoAttempt` и обрабатывать `DuplicateOrderError`; `releaseOrder` при провале без артефакта.

**Открыто.** В `ErrorCode` нет кодов для кривого тела и недоступного тарифа (сейчас 400 `internal`); `free_used` в quotes — 409; строгость пробы по IP; `admin_audit`, `checkout_events`, дневной потолок трат — позже.

**Было → стало.** Было: цены только в контракте. Стало: сервер считает цену, списывает коды без гонок и возвращает их при провале.
