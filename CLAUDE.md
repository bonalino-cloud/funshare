# Funshare — правила репозитория

Над проектом работают два вайбкодера с ИИ-агентами. У каждого своя зона. Этот файл — закон для людей и для агентов.

## Контекст перед задачей

1. `business/INDEX.md` — что делаем и для кого
2. `architecture/INDEX.md` — стек, конвейер, контракты, git-процесс
3. `plans/INDEX.md` → файл текущей фазы — что делаем сейчас

## Зоны ответственности

| Зона | Владелец | Папки |
|---|---|---|
| **FE** — интерфейс, визуал, UX-флоу | Сергей, `@bonalino-cloud` | `src/app/(site)/**`, `src/components/**`, `src/styles/**`, `src/lib/client/**`, `public/**` |
| **BE** — API, конвейер, агенты, данные, инфраструктура | Денис, `@foxawear-lab` | `src/app/api/**`, `src/server/**`, `src/workflows/**`, `drizzle/**`, `.github/workflows/**` |
| **Общая** — контракты | Оба, ревью обоих обязательно | `src/contracts/**` |

- Агент **не правит файлы чужой зоны**. Если нужно изменение там — пишет задачу владельцу (issue или комментарий в PR).
- Общаемся через контракты: FE не знает, как устроен конвейер, BE не знает, как выглядит экран. Всё, что пересекает границу, описано zod-схемой в `src/contracts/`.
- FE работает на моках (`NEXT_PUBLIC_USE_MOCKS=1`) и никогда не ждёт бэкенд.

## Ветки (подробно — `architecture/git-workflow.md`)

- `main` — продакшн. Только через PR из `dev`.
- `dev` — интеграция. Все рабочие PR — в `dev`.
- Рабочие ветки — от `dev`: `fe/p<фаза>-<задача>`, `be/p<фаза>-<задача>`, `contracts/<что>`, `fix/<что>`, `docs/<что>`.
- Никаких прямых коммитов в `main` и `dev`, никакого force-push в них.
- Конец сессии = `git push` рабочей ветки. Незапушенная работа считается потерянной.

## Код

- TypeScript strict, без `any` на границах. Всё, что приходит извне (API, LLM, скрейпер), проходит через zod-схему **до** записи в БД.
- Коммиты — Conventional Commits со скоупом: `feat(fe): …`, `fix(be): …`, `chore(contracts): …`.
- Текст статусов в UI — итог человеческими словами («Изучаем профиль…»). Коды ошибок, ответы API и reason модели — только в логи.
- Одно имя поля — один тип во всех ответах и событиях.
- Секреты только в Vercel env (`vercel env pull`). `.env*` не коммитим.

## Оркестрация кода (зона BE)

Действует для задач зоны BE и общей зоны `src/contracts/`. Для зоны FE — по решению её владельца.

**Код пишется через оркестрацию.**
- Задачу на код из плана веди через `/фаза-цикл`: оркестратор → исполнитель → проверяльщик.
- Разовую правку вне плана после написания прогони через карусель ОТДЕЛЬНЫМ субагентом-
  проверяльщиком (механика §2 `/фаза-цикл`). `/carousel` в окне, где писали код, — самопроверка,
  для кода зоны BE её недостаточно.
- Код пишет субагент-исполнитель. Карусель (`carousel/prompts/01–09`) проходит ОТДЕЛЬНЫЙ
  субагент-проверяльщик: кто писал, тот не проверяет.
- Ретро (`retrospectives/`) и `[x]` в плане ставит только оркестратор.
- Рутину оркестратор делает сам и уведомляет Дениса (решение 05.10.2026): push рабочей ветки,
  PR в `dev`, вливание при зелёном CI, `db:migrate`, живые прогоны из критерия задачи, `[x]`,
  переход к следующей задаче. Денис нужен только для решений: вкус, развилки, зона Сергея,
  `main` и релиз, необратимое (`/фаза-цикл` §4a).

**Цикл из 5 ходов после фичи** — исполнитель проходит его ДО передачи проверяльщику:
1. Найди ошибки → докажи, что они реальные → реши.
2. Что упустили (сценарии, пограничные случаи, зависимости) → докажи.
3. Это РЕАЛЬНО проблема нашего проекта (объёмы, аудитория, приоритет)? Нет — вычеркни.
4. Свежий взгляд после правок: что появилось нового, что могли сломать.
5. Security review. Особое внимание — опасной тройке: личные данные + чужой контент
   (скрейп, ответ LLM) + отправка наружу.

Инварианты для проверок — `architecture/invariants.md`.
